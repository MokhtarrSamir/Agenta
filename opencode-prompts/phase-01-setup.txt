no RAG, no MCP, no agent logic yet.

## Objective

Create a working FastAPI backend skeleton named `Backend/` (capital B, sibling to
`Frontend/`) with:
1. A layered project structure (api / core / models / services / mcp folders)
2. Docker Compose setup running MongoDB and Qdrant locally
3. A working database connection layer for both MongoDB and Qdrant
4. A single `/health` endpoint that verifies connectivity to both databases
5. Environment-based configuration using pydantic-settings

### Functional requirements:
- `GET /api/v1/health` returns JSON with the status of: the API itself, the
  MongoDB connection, and the Qdrant connection (e.g.
  `{"api": "ok", "mongodb": "ok", "qdrant": "ok"}`). If a DB is unreachable,
  that field should say `"unreachable"` or similar, NOT crash the whole app.
- Use `motor` (async MongoDB driver) since FastAPI is async — not `pymongo` sync.
- Use the official `qdrant-client` Python package.
- `app/core/config.py` must use `pydantic-settings` `BaseSettings` to load:
  `MONGODB_URI`, `MONGODB_DB_NAME`, `QDRANT_URL`, `QDRANT_PORT` (or a single
  `QDRANT_URL` if using Docker service name). Leave placeholders in the shared
  root `.env.example` for future variables we already know we'll need later
  (`GROQ_API_KEY`, `TAVILY_API_KEY`) but do NOT implement anything that uses
  them yet — just declare them as empty placeholders with comments.
- `docker-compose.yml` at the REPO ROOT (not inside Backend/) with two services:
  `mongodb` (official mongo image, persisted volume, exposed on default port)
  and `qdrant` (official qdrant/qdrant image, persisted volume, exposed on
  default ports 6333/6334). Use environment variables from `.env` where sensible
  (e.g. Mongo root username/password) rather than hardcoding.
- `Backend/Dockerfile` for the FastAPI app itself (python:3.12-slim base,
  install requirements, run with uvicorn). Add the backend as a third service
  in the root `docker-compose.yml` so `docker compose up` starts all three
  (backend + mongodb + qdrant) together, backend depending on the other two.
- `requirements.txt` should include: fastapi, uvicorn[standard], motor,
  qdrant-client, pydantic-settings, python-dotenv. Pin reasonable major versions
  but don't over-pin exact patch versions.

## Architecture Constraints

- Follow separation of concerns strictly: endpoints in `api/v1/endpoints/` must
  contain ONLY request/response handling, no business logic and no direct DB
  driver calls — route logic like "check mongo connection" should live in
  `core/database.py` as a reusable function that the endpoint calls.
- Do not add authentication, rate limiting, RAG logic, MCP logic, or any
  ingestion/embedding code in this phase — this is setup-only.
- Do not modify anything inside `Frontend/`.
- Do not create a new root README content beyond a minimal "how to run this
  backend locally" section — full project documentation comes in a later phase.

## Error Handling

- If MongoDB or Qdrant is unreachable at startup, the FastAPI app should still
  start (don't crash the whole process) — the `/health` endpoint should simply
  report the failure per-service so we can debug during development.
- Config loading should raise a clear, readable error if a required env var is
  genuinely missing (not just print a generic traceback).

## Testing & Verification

- Verify `GET http://localhost:<port>/api/v1/health` returns 200 with both
  databases reporting "ok".
- If anything fails to build or run, report the exact error and your diagnosis
